## v11 — Recuperar contraseña

Link de "olvidé mi contraseña" en el login, para credenciales (Google no lo necesita: no tiene password). Mismo criterio que la firma remota (Fase 10): token no adivinable + expiración + un solo uso, guardado hasheado. Construida y probada en local (build/lint/tests en verde — 143 tests; verificado extremo a extremo contra la base real: token válido cambia la contraseña y se consume, reintento con el mismo token se rechaza, token vencido/inexistente se rechaza, email inexistente no revela nada). **Falta:** probar el envío real del email en producción (Resend) y el flujo en un celular real — la UI reusa los mismos componentes de `/login`, ya validados en 375px.

- **Modelo `PasswordResetToken`** (migración `add_password_reset_tokens`): `userId`, **`tokenHash`** (sha256, único — el token en texto plano solo viaja en el link del email, nunca se guarda), `expiresAt`, `usedAt` (null = pendiente). Lógica pura en `src/lib/password-reset.ts` (`generatePasswordResetToken`, `hashPasswordResetToken`, `isPasswordResetTokenUsable`; TTL 1 hora), testeada.
- **`/forgot-password`** (pública, excluida del proxy): pide el email, siempre responde el mismo mensaje genérico exista o no el usuario (evita enumeration). Si existe y está activo: borra los tokens pendientes anteriores de ese usuario (solo el link más nuevo vale), crea uno nuevo y manda el email (Resend directo, texto fijo en español — es para empleados, no pasa por el diccionario i18n del cliente). Sin `RESEND_API_KEY`/`EMAIL_FROM`, el token se crea pero el email se omite con un warning (mismo criterio que el acta).
- **`/reset-password/[token]`** (pública, excluida del proxy): la página valida el token server-side antes de mostrar el form (si venció/no existe, muestra error + link para pedir uno nuevo). La action `resetPassword` **re-valida** el token (por si venció entre que se mostró la página y el submit) y lo consume de forma atómica dentro de una transacción interactiva (`updateMany` con `usedAt: null` como guard de un solo uso; si no afecta filas, no llega a tocar el password — evita la carrera de actualizar el password con un token ya consumido). Contraseña mínimo 6 caracteres, mismo criterio que el cambio de contraseña desde el perfil. Redirige a `/login?reset=1`, que muestra "Contraseña actualizada".
- **Proxy** (`src/proxy.ts`): `forgot-password` y `reset-password` se suman a la lista de rutas públicas excluidas del matcher (mismo grupo que `sign`/`api/sign`).
- **Login** (`login-form.tsx`): link "¿Olvidaste tu contraseña?" debajo del campo de contraseña.

## v34 — Fix real de "Borrar un usuario": nombre congelado en toda interacción

El "Borrar un usuario" de v33 quedaba incompleto: `Inspection.userId` y `ConditionSettingsEdit.editedById` eran relaciones **obligatorias**, así que borrar un usuario con al menos una entrega/devolución firmada (el caso típico de cualquier empleado real) tiraba **P2014** ("violaría la relación obligatoria"), no P2003 — el código solo atajaba P2003, así que el error llegaba sin capturar hasta el `error.tsx` global ("Algo salió mal"), sin mensaje claro. Además, pedido del dueño: al borrar un usuario, **el nombre tiene que seguir apareciendo tal cual** en todo lo que cargó (entregas/devoluciones, notas de equipo, Caja, daños, tareas, WhatsApp) — no un "—" genérico.

- **Patrón "nombre congelado"** (mismo criterio que `paymentMethodName`/`categoryName` en `CashMovement`, ya existente desde v8/v29): cada relación a `User` que se muestra en algún lado suma una columna `*Name` de solo texto, escrita una vez al crear la fila y nunca actualizada — sobrevive a que el usuario se borre, se rebautice, o cambie de rol. Aplicado a: `Inspection.userName`, `ConditionSettingsEdit.editedByName`, `VehicleNote`/`RentalNote` (`createdByName`/`resolvedByName`), `Damage` (`reportedByName`/`repairedByName`), `Task` (`createdByName`/`assignedToName`), `CashMovement`/`CashMovementEdit`/`SafeMovement`/`SafeMovementEdit` (`createdByName`/`deletedByName`/`editedByName`), `RentalQuote.createdByName`, `WhatsAppMessage.sentByName`, `WhatsAppBotEscalation.resolvedByName`. Helper `displayName(user)` (`src/lib/user-display.ts`) resuelve el nombre desde la sesión con un fallback defensivo (el tipo de `next-auth` deja `name` nullable aunque `User.name` sea obligatorio en la base).
- **Las dos relaciones obligatorias pasan a opcionales con `onDelete: SetNull`**: `Inspection.userId` y `ConditionSettingsEdit.editedById` — el resto ya eran opcionales desde que se crearon (`onDelete: SetNull` por default de Prisma), solo les faltaba el nombre congelado para no mostrar "—" al borrar al autor.
- **Migración `add_user_delete_name_snapshots`**: agrega las columnas como nullable, hace backfill (`UPDATE ... FROM users`) para todo lo que ya tiene el `*_id` cargado, aplica un fallback fijo ("Desconocido"/`AUTO_IMPORT_CREATOR_LABEL`) a las filas huérfanas preexistentes, y recién ahí exige `NOT NULL` donde el modelo lo requiere. Migración aparte `add_rental_quote_created_by_name` (se sumó después de auditar `calendar.ts` y encontrar que `RentalQuote.createdByName` también se mostraba en el detalle de un presupuesto).
- Como consecuencia, varios `include: { xxx: { select: { name: true } } }` que solo estaban para leer un nombre se sacaron (ya no hace falta el join): `acta/index.ts`, `rental-detail-queries.ts`, `vehicle-detail-queries.ts`, `settings/general/page.tsx`, `calendar.ts`, `cash.ts`, `safe.ts`, `third-party-accounts.ts`, `tasks.ts`, `whatsapp/conversations.ts`.
- `deleteUser` (`src/app/(app)/users/actions.ts`) queda simplificado: con las dos relaciones obligatorias resueltas, el catch de P2003 pasa a ser un caso de borde defensivo en vez del camino esperado.
- **Verificado end-to-end contra la base local**: se creó un usuario de prueba, se le cargó una `VehicleNote` y una `Inspection` (el caso que antes crasheaba), se lo desactivó y se lo borró — sin error, y ambas filas conservan el nombre (`createdByName`/`userName`) con el `*Id` en `null`. Build/lint/tsc/tests en verde (468 tests).
- **No incluido a propósito**: `RentalDocument.uploadedById`, `SignatureRequest.createdById` y `WhatsAppConversation.assignedToId` no se tocaron — ninguno de los tres se muestra hoy en ninguna pantalla (el de `WhatsAppConversation` es el campo de "Asignado a" que v25 sacó de la UI a pedido del dueño), así que un nombre congelado ahí no tendría ningún consumidor.

## v87 — Logout automático por inactividad a 10 minutos

Antes 1 hora (v33). `session.maxAge: 10*60` en `src/auth.config.ts` + `INACTIVITY_LIMIT_MS` en `inactivity-logout.tsx` (tienen que quedar iguales). `updateAge` baja a 60s: el JWT puede vencer hasta `updateAge` antes de lo que marca la última request, y con 10 min eso tiene que quedar por debajo del aviso de 60s del cliente. **Ojo con el wizard sin señal:** el cliente cuenta taps como actividad, pero el servidor solo renueva la sesión con requests — si un empleado pasa más de 10 min en la entrega/devolución sin ninguna request (modo avión), al guardar la sesión ya venció y tiene que volver a loguearse (el borrador sobrevive en localStorage y la evidencia en IndexedDB).

## v91 — El propietario no se desconecta por inactividad

Pedido del dueño: la cuenta del propietario (`User.owner`) mantiene la sesión iniciada por tiempo indeterminado; el resto sigue con el corte de 10 min de v87. tsc/lint/870 tests en verde (+5 en `session-idle.test.ts`); verificado contra el servidor local con cookies firmadas a mano (empleado con 15 min sin actividad → login; con 5 min → adentro; propietario con 15 min y con 300 días → adentro) y con un login real (cookie a 365 días, renovada en cada request). Sin migración.

- **Auth.js no admite un vencimiento por usuario** (firma todos los JWT con el mismo `session.maxAge`). Por eso `maxAge` pasa a ser largo para todos (`SESSION_MAX_AGE_S`, 1 año, renovado en cada request) y el corte por inactividad lo hace `applyIdleTimeout` (`src/lib/session-idle.ts`, pura y testeada) desde el callback `jwt` de `auth.config.ts` (el que corre el proxy en cada request) y de `auth.ts`: guarda `lastSeen` en el token y devuelve `null` (Auth.js borra la cookie) si quien no es propietario pasó más de `IDLE_TIMEOUT_MS` (10 min) sin requests. `updateAge` se sacó (no aplica a sesiones JWT). Un token emitido antes del cambio (sin `lastSeen`) cuenta como activo.
- **Aviso "¿Seguís ahí?"** (`InactivityLogout`): usa el mismo `IDLE_TIMEOUT_MS` y no se monta para el propietario (`getSessionUser().realOwner`, que no cambia con "Ver como empleado").
- **Límites conocidos:** "indeterminado" = mientras abra la app al menos una vez al año (si no, vence la cookie). El flag `owner` se lee del token al iniciar sesión: si algún día se le quita a una cuenta, su sesión ya abierta sigue sin vencer hasta que cierre sesión a mano (no hay revocación de JWT). Un celular perdido con la sesión del propietario abierta queda con acceso total hasta cerrar sesión desde ese dispositivo o rotar `AUTH_SECRET` (cierra la sesión de todos).
